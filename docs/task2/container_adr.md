### Описание решения (Container, основное)

| **Тема** | **Описание** |
|:---------|:-------------|
| UI: web | web на React — для всех ролей. |
| UI: mobileApp | mobileApp на Flutter — для зоотехника и дежурного, им надо в поле. |
| UI: apiGateway | apiGateway на Kong — точка входа, всё от UI идёт через него. |
| Бизнес-логика | coreApi на Java (Spring Boot) — бизнес-логика. |
| coreApi: что делает | Читает dataWarehouse, кидает события в rabbitMQ, ходит в videoIngest за камерами, в erpSystem за финансами. |
| coreApi: компоненты | Внутри девять компонентов: Controller, AnimalService, CameraService, EventService, ErpService, репозиторий к базе, два клиента и публикатор. |
| Приём: videoIngest | videoIngest на Go принимает RTSP с камер. |
| Приём: loraIngest | loraIngest на Go — MQTT с LoRaWAN. |
| Приём: weatherIngest | weatherIngest на Python — данные с метеостанций. |
| Приём: rabbitMQ | Все три пишут в rabbitMQ. |
| Обработка: aiAdapter | aiAdapter на Go работает с внешним AI. |
| aiAdapter: компоненты | Внутри пять: FrameConsumer читает кадры, FrameProcessor готовит, AiClient шлёт в AI по gRPC, ResultHandler обрабатывает, AiEventPublisher публикует обратно. |
| Обработка: notifications | notifications на Node.js рассылает SMS/Push/Email. |
| Обработка: resourceService | resourceService на Python считает прогноз воды и корма. |
| Обработка: moduleAnalytic | moduleAnalytic на Python+Spark — аналитика эффективности. |
| Обработка: dataWriter | dataWriter на Go — единственный, кто пишет в хранилища. |
| Хранилище: dataLake | dataLake на MinIO (S3) — сырые данные: видео, телеметрия, события. |
| Хранилище: dataWarehouse | dataWarehouse на ClickHouse — структурированные, для аналитики и UI. |
| Шина | rabbitMQ — единая шина для всех. |
| Поток: видео | Камеры → videoIngest → rabbitMQ → aiAdapter → AI → обратно → rabbitMQ → notifications → провайдер → юзер. |
| Поток: IoT | Параллельно LoRaWAN и метеостанции → ingest → rabbitMQ. |
| Поток: запись | В хранилища пишет только dataWriter. |
| Поток: coreApi | coreApi обслуживает UI синхронно, события в брокер кидает как побочный эффект. |
| Поток: BI | biSystem читает из dataWarehouse напрямую через SQL/ODBC. |

### <a name="_bjrr7veeh80c"></a>**Альтернативы** ---→ [Контейнерная диаграмма (альтернативное)](container_alt.md)

### Описание решения (Container, альтернатива)

| **Тема** | **Описание** |
|:---------|:-------------|
| Ключевое отличие | Видео-контур уходит вендору, добавляются vmsClient и eventStore. |
| UI | web, mobileApp, apiGateway — без изменений. |
| Бизнес-логика | coreApi читает не только dataWarehouse, но и eventStore. |
| coreApi: клипы | За клипами ходит не в VMS напрямую, а в vmsClient. |
| coreApi: компоненты | Внутри те же девять компонентов. |
| Приём данных | Только IoT: loraIngest и weatherIngest. |
| Приём: видео | videoIngest нет — видео идёт прямо в VMS. |
| Обработка: vmsClient | vmsClient на Go принимает webhook от VMS, запрашивает клипы по REST. |
| vmsClient: компоненты | Внутри пять: WebhookController, EventFilter, EventPublisher, ClipClient, VmsApiClient. |
| Обработка: triggerEngine | triggerEngine на Java — правила: событие VMS + данные с датчиков = триггер. |
| Обработка: остальное | notifications, resourceService, moduleAnalytic, dataWriter — как в основном. |
| Хранилище: dataWarehouse | dataWarehouse на ClickHouse — аналитика. |
| Хранилище: eventStore | eventStore на PostgreSQL — оперативные события и триггеры. |
| Хранилище: dataLake | dataLake нет — сырое всё у VMS. |
| Шина | rabbitMQ — та же. |
| Поток: события | VMS → webhook → vmsClient → rabbitMQ → triggerEngine → rabbitMQ → notifications → провайдер → юзер. |
| Поток: coreApi | coreApi обслуживает UI, читает из двух хранилищ, кидает события в брокер, за клипами ходит в vmsClient. |
| Поток: IoT | IoT-поток не меняется. |
| Поток: BI | biSystem читает из dataWarehouse напрямую. |
| Вывод | Контейнеров меньше, инфраструктуры меньше, но зависимость от вендора выше. |
| Риск | Упадёт VMS — встанет весь видео-контур. |
| Плюс | Зато запуск быстрее и фокус на бизнес-логике. |


| **№** | **Альтернатива** | **Недостатки**                         |
|:-----:|:-----------------|:---------------------------------------|
|   1   | VMS-центричное   | Ограничения VMS, подписка, зависимость, отсутствие edge |

**Недостатки, ограничения, риски**

| **№** | **Решение**                          | **Недостатки**                          | **Ограничения**                                        | **Риски**                                                     |
|:-----:|:-------------------------------------|:----------------------------------------|:-------------------------------------------------------|:--------------------------------------------------------------|
|   1   | `coreApi` (Java, Spring Boot)        | God Object при росте числа сценариев    | Зависит от `dataWarehouse`, `videoIngest`, `erpSystem` | При падении `coreApi` — UI недоступен                         |
|   2   | `aiAdapter` (Go)                     | Задержка при gRPC-стриме                | Зависит от внешнего `aiTracking`                       | При недоступности AI — события не формируются                 |
|   3   | `notifications` (Node.js)            | Смешение ролей (правила + доставка)     | Зависит от `rabbitMQ` и `notificationProvider`         | При падении `notificationProvider` — уведомления уходят в DLQ |
|   4   | `rabbitMQ`                           | Единая точка отказа                     | Пропускная способность                                 | При перегрузке — потеря событий (митигация: DLQ)              |
|   5   | `dataWarehouse` (ClickHouse)         | Не подходит для транзакционных запросов | Оперативные запросы медленнее                          | При отказе — UI не работает                                   |
|   6   | `dataLake` (MinIO S3)                | Дорогое хранение больших объёмов        | Пропускная способность S3                              | При отказе — видео не сохраняется                             |
|   7   | `videoIngest` (Go)                   | Зависит от стабильности сети камер      | Пропускная способность RTSP                            | При отказе камер — нет видеопотока                            |
|   8   | Edge-обработка (гибрид edge + cloud) | Сложнее в разработке и поддержке        | Нужен edge-деплой на каждой ферме                      | При отказе edge — локальные сценарии не работают              |
